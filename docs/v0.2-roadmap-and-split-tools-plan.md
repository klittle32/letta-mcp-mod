# Letta MCP Adapter v0.2 Roadmap and Split-Tools Plan

Status: Milestones 1-2 implemented; Milestones 3-7 planned

This document records the product direction, issue ordering, and implementation
plan agreed in the Delta planning thread. It supersedes earlier suggestions to
preserve the v0.1 model-facing surface or expand the adapter into a general
toolbox.

## Product Direction

This project brings the functionality and usability of
[`pi-mcp-adapter`](https://github.com/nicobailon/pi-mcp-adapter) to Letta Code.

The product is:

> A lazy, context-efficient MCP gateway for Letta Code.

It is intended for the project owner and any other Letta Code user who wants
MCP access without eagerly loading every MCP tool schema into model context.

### Decisions

- MCP remains the product scope and architectural center.
- `pi-mcp-adapter` remains the primary feature, API, and usability reference,
  adapted to Letta Code's public mod APIs.
- Breaking changes from v0.1 are acceptable.
- The implementation does not need compatibility modes for the v0.1 tool API,
  config, cache, OAuth state, SSE support, or Node version.
- The old model-facing surface does not need to remain registered as a
  comparison baseline; Git history already preserves it.
- The project will not be renamed to "Toolbox." Removing MCP terminology from
  model-facing tool names is a routing/usability choice, not a change in product
  identity.
- A general CLI/script/HTTP tool catalog is out of scope. Issue #3 is not part
  of this roadmap.
- Native Letta MCP coexistence is not on the critical path unless duplicate
  ownership becomes an observed problem.
- Cache connections and metadata refresh are implementation details. Users and
  agents should not have to manage cache state for `search_tools` to return
  useful, current results.

## Issue Roadmap

### Milestone 1: Replace the model-facing proxy

Issue: [#2](https://github.com/klittle32/letta-mcp-mod/issues/2)

- Remove the model-facing `mcp` tool.
- Add `search_tools`.
- Add `call_tool`.
- Use object-valued call arguments.
- Keep setup, status, reconnect, and OAuth on `/lmcp`.
- Preserve optional direct tools.

### Milestone 2: Complete output guarding

Issue: [#10](https://github.com/klittle32/letta-mcp-mod/issues/10)

Status: implemented. See
[`milestone-2-output-guard-plan.md`](./milestone-2-output-guard-plan.md).

- Enforce one aggregate result limit.
- Spill oversized results to private files.
- Return an actionable pointer to retained output.
- Cover text, structured content, and resources.
- Prune old spill files.

The v0.1 renderer already truncates individual text and JSON values. This
milestone addresses aggregate bounds and retained overflow rather than adding
the first output limit.

### Milestone 3: Upgrade the protocol foundation

Issues:

- [#4](https://github.com/klittle32/letta-mcp-mod/issues/4): MCP SDK 2 and
  protocol version negotiation.
- [#7](https://github.com/klittle32/letta-mcp-mod/issues/7): current
  Streamable HTTP behavior and SSE removal.

These belong together because the SDK migration changes transport APIs and
protocol behavior. Breaking transport changes are acceptable.

### Milestone 4: Upgrade metadata and caching

Issues:

- [#5](https://github.com/klittle32/letta-mcp-mod/issues/5): `ttlMs`,
  `cacheScope`, identity isolation, and invalidation.
- [#9](https://github.com/klittle32/letta-mcp-mod/issues/9): titles,
  annotations, output schemas, and icons.

Both issues change the persisted cache model and should share one deliberate
cache-version replacement. A legacy cache reader is not required.

### Milestone 5: Bring approvals up to reference quality

Issue: [#11](https://github.com/klittle32/letta-mcp-mod/issues/11)

- Add per-tool approval patterns.
- Add once/session/deny behavior.
- Scope session approvals to the argument payload.
- Apply policy consistently to proxy and direct calls.
- Add include/exclude symmetry.

This follows richer metadata so policy and presentation can use the same
catalog representation.

### Milestone 6: Harden OAuth

Issue: [#8](https://github.com/klittle32/letta-mcp-mod/issues/8)

- Add resource and issuer validation.
- Key state by issuer.
- Use current client-discovery behavior.
- Store credentials securely.
- Support scope step-up where the SDK and Letta host permit it.

Reconfiguration or reauthentication is acceptable. The deployment format
(single-file bundle or a supported package-based mod) should be resolved from
current Letta capabilities while planning this milestone.

### Milestone 7: Add modern result flows

Issue: [#6](https://github.com/klittle32/letta-mcp-mod/issues/6)

- Recognize complete, input-required, and task results.
- Integrate user input and task polling only through public Letta capabilities.
- Return clear errors when the host cannot complete a requested flow.

### Later hardening

Issue: [#1](https://github.com/klittle32/letta-mcp-mod/issues/1)

Native MCP ownership and collision detection can be addressed if duplicate
registration is observed or Letta exposes an authoritative public ownership
API. It does not block the core adapter port.

### Out of scope

Issue: [#3](https://github.com/klittle32/letta-mcp-mod/issues/3)

The proposed general backend catalog for CLI, script, and HTTP tools is a
different product direction and is excluded.

### Tracking

Issue [#12](https://github.com/klittle32/letta-mcp-mod/issues/12) remains the
tracking epic and should be updated later to reflect this milestone order.

## Selected First Vertical Slice

The first implementation slice is a clean replacement of the multifunction
model-facing `mcp` proxy with `search_tools` and `call_tool`.

No implementation begins until this plan is approved.

## Product Contract

### `search_tools`

```ts
search_tools({
  query: string,
  limit?: number
})
```

Behavior:

- Search tools across configured MCP servers.
- Transparently obtain or refresh metadata when necessary.
- Return a bounded set of useful matches.
- Include each match's callable name, description, and full input schema.
- Report authentication or unavailable-server blockers concisely.
- Do not make users or agents manage cache freshness as a separate workflow.

Connection, cache, and refresh choices are internal implementation details and
should be evaluated by responsiveness, reliability, and safety.

### `call_tool`

```ts
call_tool({
  name: string,
  args: Record<string, unknown>
})
```

Behavior:

- Call a tool identified by `search_tools`.
- Pass object-valued arguments to the MCP call without requiring a JSON string.
- Reuse existing lazy connection, resolution, permission, transport, and
  result-rendering behavior.
- Return concise setup or authentication guidance when execution is blocked.
- Do not expose status, connect, reconnect, or OAuth modes.

### Human command surface

`/lmcp` remains responsible for:

- Status.
- Setup.
- Cached tool listing.
- Explicit reconnects.
- OAuth start, completion, status, and clearing.

### Direct tools

Optional cache-backed direct tools remain supported and continue to invoke the
same runtime call path.

## Implementation Plan

### 1. Split registration in `src/mod.ts`

- Remove `createMcpTool`.
- Define and register `search_tools`.
- Define and register `call_tool`.
- Do not register a legacy `mcp` alias.
- Preserve direct-tool registration and `/lmcp` registration.

### 2. Refactor `src/features/proxy-tool.ts`

- Remove the multifunction model-facing schema and dispatcher.
- Retain or extract reusable catalog state, status, search, schema formatting,
  and tool-list formatting.
- Keep human command helpers independent from model-facing tool definitions.
- Rename the module if doing so makes its remaining catalog responsibility
  clearer; do not perform unrelated renames.

### 3. Update `src/runtime.ts`

- Decouple runtime context from `McpProxyArgs`.
- Change `callTool` to accept parsed object arguments.
- Remove JSON-string parsing from the normal call path.
- Add an asynchronous search path that can obtain or refresh metadata when
  current catalog data is unavailable.
- Preserve cancellation and concise transport/authentication failures.
- Preserve lazy call-time connection and exact target resolution.

### 4. Update permissions

In `src/features/permissions.ts`:

- Recognize `search_tools` as the read/search surface.
- Recognize `call_tool` and inspect its `name` and object-valued `args`.
- Keep permission checks side-effect-free: they must not connect, refresh, or
  make network calls.
- Preserve fail-closed behavior for ambiguous or unconfigured targets.
- Preserve approval/execution fingerprinting for risky calls.

### 5. Update direct tools

In `src/features/direct-tools.ts`:

- Pass object arguments to the runtime without JSON serialization.
- Preserve cache-backed registration and existing naming behavior.

### 6. Preserve `/lmcp`

In `src/features/mcp-command.ts` and OAuth helpers:

- Continue exposing status, setup, reconnect, listing, and OAuth actions.
- Update imports after proxy/catalog helpers are extracted.
- Do not add these operations to either model-facing tool.

### 7. Update documentation

In `README.md`:

- Describe `search_tools` followed by `call_tool` as the model workflow.
- Remove model-facing `mcp(...)` examples.
- Keep the Letta MCP Adapter product identity.
- Keep `/lmcp` setup, status, reconnect, and OAuth instructions.
- Document object-valued call arguments.

### 8. Update focused tests

The existing proxy-oriented tests should be rewritten around the two tools
rather than preserved as legacy compatibility tests.

Likely affected suites:

- `tests/mod.test.ts`
- `tests/proxy-tool.test.ts`
- `tests/proxy-connect.test.ts`
- `tests/proxy-tool-call.test.ts`
- `tests/proxy-tool-http.test.ts`
- `tests/proxy-oauth.test.ts`
- `tests/permissions.test.ts`
- `tests/direct-tools-runtime.test.ts`
- `tests/runtime-call.test.ts`
- `tests/mcp-command.test.ts`

Test filenames may be renamed to match the new surface.

## Alternatives Rejected

### Keep one multifunction `mcp` tool

Rejected because issue #2 records a Letta-specific routing and naming problem.
The new surface gives discovery and execution one clear responsibility each.

### Register legacy and split tools together

Rejected because backward compatibility is not required and dual registration
would add configuration, tests, and model ambiguity without product value.

### Preserve JSON-string `args`

Rejected because compatibility is not required and object-valued arguments are
the clearer model-facing API.

### Rename the product to Toolbox

Rejected because MCP remains the product scope. Generic model-facing tool names
do not require a broader product identity.

### Include output spill, SDK 2, or cache-format changes in this slice

Rejected to keep the first slice focused on issue #2. Those changes have
separate milestones and completion criteria.

## Risks

- Search may need to combine useful partial results with server-specific
  authentication or connection failures.
- The permission overlay currently resolves calls from cached metadata before
  runtime execution; the split must preserve safety without preventing valid
  refreshed calls.
- Human commands currently import status and state helpers from
  `proxy-tool.ts`; extraction must not accidentally change `/lmcp`.
- Direct tools currently bridge object arguments into the runtime's
  JSON-string API; changing the runtime API affects both proxy and direct call
  tests.
- Broad search results can still be large. This slice must return a bounded
  number of matches; aggregate call-result retention remains milestone 2.

## Done Conditions

The slice is complete when:

1. Letta registers `search_tools` and `call_tool` as the proxy surface.
2. The model-facing `mcp` tool is absent.
3. Search returns bounded matches with callable names, descriptions, and input
   schemas.
4. Search works when metadata has to be obtained or refreshed.
5. `call_tool` passes object arguments to the resolved MCP tool.
6. Status, setup, reconnect, and OAuth are absent from model-facing schemas and
   remain available through `/lmcp`.
7. Optional direct tools continue to work.
8. Permission checks cover both new tools without performing live work.
9. Focused search, call, connection, HTTP, OAuth, direct-tool, command, and
   permission tests pass.
10. The full test suite passes.
11. TypeScript typechecking passes.
12. The bundled mod build passes.

### Milestone 1 verification

- The model surface is exactly `search_tools` and `call_tool`, followed by any
  explicitly enabled cache-backed direct tools.
- The focused and full test suite passes: 291 tests across 24 files. Obsolete
  multifunction-proxy tests were replaced rather than retained as compatibility
  tests.
- `bun run typecheck` passes.
- `bun run build` produces `dist/letta-mcp-adapter.mjs`.
